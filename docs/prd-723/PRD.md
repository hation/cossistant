## 1. 产品概述

Cossistant 是一个**无头实时客户支持平台**，为开发者和 SaaS 团队提供可嵌入的聊天 Widget、AI 智能客服、知识库检索、实时消息系统，支持云服务和自托管两种模式。

**核心设计原则**（已在架构中体现）：
1. 开发者优先：API 驱动、TypeScript 全栈、完整 OpenAPI 文档
2. 实时优先：WebSocket 全链路、无轮询、跨实例 Pub/Sub
3. AI 原生：双管道设计（主管道实时 + 后台管道异步）
4. 故障友好：多级降级、停电模式、硬限制自动关闭

### 3.2 AI 对话管道

#### 3.2.1 双管道架构

**主管道（实时，访客消息到达时执行）**：
1. 消息接收与验证
2. 访客上下文检索（历史消息、浏览路径）
3. 知识库向量检索（Top 3 相关片段）
4. 构建 Prompt（系统提示 + 上下文 + 知识片段）
5. 调用 LLM 生成回复
6. 流式推送给访客
7. 保存消息到数据库
8. 异步启动后台管道

**后台管道（异步，不阻塞回复）**：
1. 对话标题自动生成（基于前 3 条消息）
2. 知识缺口分析（访客问题知识库没有覆盖）
3. 意图分类（自动打标签）
4. 情感分析（正面/中性/负面）
5. 触发自动化规则（如负面情绪自动通知主管）

#### 3.2.2 AI 回复决策逻辑

```
访客消息到达
       │
       ▼
    检索知识库
       │
       ├─ 相似度 > 0.9 → 直接使用知识回答 ✅
       │
       ├─ 相似度 0.7-0.9 → 组合多个知识片段回答
       │
       ├─ 相似度 0.5-0.7 → 给出参考，同时询问更多信息
       │
       └─ 相似度 < 0.5 →
              │
              ├─ 是否要转接人工？
              │   └─ 是 → 通知客服，告知访客正在转接
              │
              └─ 否 → 尝试澄清问题：
                   "您是指 [猜测 1] 还是 [猜测 2]？或者可以描述更详细一些吗？"
```

#### 3.2.3 知识澄清流

当 AI 不确定答案时，启动知识澄清流程：
1. 向访客确认问题意图
2. 获取更多信息后二次检索
3. 仍无法回答 → 转接人工
4. 同时记录该问题 → 知识库待优化条目

### 3.3 知识库 RAG 系统

#### 3.3.1 知识源类型

| 源类型 | Free | Hobby | Pro |
|--------|------|-------|------|
| **URL 爬取** | 5 个 | 无限 | 无限 |
| **FAQ 条目** | 5 条 | 无限 | 无限 |
| **文件上传** | 2 个 | 无限 | 无限 |
| **自定义文本** | ✅ | ✅ | ✅ |
| **单源爬取页数** | 5 页 | 1000 页 | 1000 页 |
| **训练频率限制** | 180 分钟 | 10 分钟 | 即时 |

#### 3.3.2 训练流程

```
用户输入 URL / 上传文件
       │
       ▼
    内容提取
       ├─ 网页：Firecrawl 爬取 → HTML 转 Markdown
       ├─ PDF：文本提取 + 分块
       └─ 纯文本：直接分块
       │
       ▼
    语义分块
       │
       ▼
    向量化（OpenAI Embedding）
       │
       ▼
    存储到 PostgreSQL + pgvector
       │
       ▼
    触发索引优化（HNSW）
       │
       ▼
    完成，显示训练统计
```

#### 3.3.3 检索参数

| 参数 | 值 | 说明 |
|------|----|------|
| **检索 Top K** | 3 | 取最相关的 3 个片段 |
| **相似度阈值** | 0.7 | 低于此值的结果不使用 |
| **重排序** | 启用 | 向量检索后交叉编码器重排序 |
| **上下文窗口** | 4096 tokens | 留给知识的 Token 预算 |
| **分块大小** | 512 tokens | 每个知识片段的 Token 数量 |
| **分块重叠** | 64 tokens | 相邻块之间的重叠 |

### 3.4 实时消息系统

#### 3.4.1 WebSocket 连接管理

**多实例架构**：
- 多 API 实例同时运行
- 每个实例维护本地连接注册表（内存 Map）
- Redis Streams 作为跨实例消息总线
- 访客连接到任意实例，客服连接到任意实例
- 消息通过 Redis 广播到目标连接所在的实例

**连接生命周期**：
1. 访客打开 Widget → 建立 WebSocket 连接
2. 注册到本地连接注册表
3. 订阅 Redis 频道（website:{id}）
4. 心跳检测（每 30 秒 ping）
5. 连接断开 → 从注册表移除 → 广播离线事件

#### 3.4.2 实时事件类型

| 事件 | 触发时机 | 接收方 |
|------|---------|--------|
| `message:created` | 新消息发送 | 对话相关的所有人 |
| `message:updated` | 消息编辑/删除 | 对话相关的所有人 |
| `typing:start` | 开始输入 | 对方 |
| `typing:stop` | 停止输入 | 对方 |
| `conversation:assigned` | 对话分配给客服 | 目标客服 |
| `agent:online` | 客服上线 | 组织内所有人 |
| `agent:offline` | 客服下线 | 组织内所有人 |
| `visitor:joined` | 新访客打开聊天 | 所有在线客服 |

| 计量项 | 超限行为 |
|--------|---------|
| 对话数 | 新访客消息自动回复："已达本月限制，访客留言我们会邮件回复" |

#### 3.6.3 故障降级机制（停电模式）

当 Polar 计费平台不可用时：
1. 所有计划检查使用缓存数据（最多 10 秒）
2. 缓存也失效时 → 自动升级到 Pro 计划功能
3. **所有硬限制自动关闭**，不中断服务
4. 后台静默重试 Polar 连接
5. 恢复后后台异步核对用量

## 4. 非功能需求

### 4.1 性能目标

| 指标 | 目标值 | 测量点 |
|------|--------|--------|
| Widget 脚本加载 | < 500ms | CDN + 浏览器缓存 |
| API 响应时间 | < 200ms（P95） | 所有 REST 端点 |
| AI 回复生成 | < 2s（P95） | 访客发消息到开始显示回复 |
| 知识库检索 | < 500ms | 向量查询 + 重排序 |
| 消息送达延迟 | < 300ms（P95） | 客服发送到访客收到 |
| 工作台首屏加载 | < 2s | 登录后到可操作 |

### 4.2 可用性目标

| 层级 | 可用性 | 年 downtime |
|------|--------|------------|
| 核心消息路径 | 99.99% | < 53 分钟 |
| AI 功能 | 99.9% | < 9 小时 |
| 管理后台 | 99.5% | < 44 小时 |

### 4.3 安全要求

- 所有传输 HTTPS/TLS 1.3
- 密码 bcrypt 哈希（cost 12）
- 所有敏感数据字段级加密
- API Key 权限范围控制
- Webhook 签名验证
- 完整审计日志（所有修改操作）
- 多租户数据隔离（组织级 + 网站级）
