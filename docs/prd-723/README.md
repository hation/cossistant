## 🔄 反向推导说明

**这三份文档不是传统的"正向产品设计"，而是"基于已实现代码的反向产品化梳理"**。

### 推导依据来源

| 架构文档 | 对应产品内容 |
|---------|------------|
| `01-SYSTEM-OVERVIEW.md` | 整体架构 → 产品定位、技术栈、模块划分 |
| `03-REAL-TIME-MESSAGING.md` | WebSocket 实时系统 → 客服工作台、实时协作 |
| `04-AI-CONVERSATION.md` | AI 双管道 → AI 自动回复、智能建议、知识澄清 |
| `05-KNOWLEDGE-BASE.md` | RAG 系统 → 知识库训练、向量检索 |
| `06-VISITOR-TRACKING.md` | 访客追踪 → 归因分析、访客画像 |
| `07-BILLING.md` | 计费系统 → 三级订阅、计划对比、故障降级策略 |
| `09-DATA-MODEL.md` | 数据库 Schema → 信息架构、实体关系 |
| `10-TECH-STACK.md` | 技术选型 → 非功能需求、性能指标 |

### 推导原则

1. **代码存在 = 功能已实现**
   - 文件路径存在 → 功能模块存在
   - 函数/类存在 → 具体功能点存在
   - 配置项存在 → 功能可配置

2. **架构决策 = 产品权衡**
   - "故障降级"、"停电模式" → 产品可用性优先策略
   - "按网站计费"而非"按座席" → 商业模式选择
   - "自托管完整支持" → 开源/商业双轨策略

3. **技术约束 → 产品约束**
   - 向量检索 P95 < 500ms → 产品性能承诺
   - 30 天滚动窗口计量 → 计费周期定义
   - 多租户隔离 → 安全与合规要求

## 🎯 核心决策摘要

### 商业模式决策

| 决策 | 说明 | 架构证据 |
|------|------|---------|
| 三级订阅 | Free / Hobby / Pro | `07-BILLING.md` 完整计划配置表 |
| 按网站计费 | 每个网站独立订阅，不是按座席 | Website 实体 + 每站 plan_id |
| 30 天滚动计量 | 非自然月，滚动窗口统计用量 | 数据库中的 rolling window 设计 |
| 停电模式 | 计费平台故障不中断服务 | 多级缓存 + 降级机制代码 |
| 自托管免费 | 自部署用户无任何功能限制 | self_hosted 特征判断逻辑 |

### 产品定位决策

| 决策 | 说明 | 架构证据 |
|------|------|---------|
| 无头架构 | API 优先，提供嵌入 Widget 而非完整产品 | OpenAPI 规范、REST/v1 接口完整 |
| 开发者优先 | TypeScript 全栈、自托管友好、文档完善 | 技术栈文档、完整代码结构 |
| AI 原生 | AI 不是附加功能，贯穿整个消息流程 | Primary + Background 双管道设计 |
| 实时优先 | WebSocket 全链路，无轮询 | Redis Streams 跨实例事件总线 |
